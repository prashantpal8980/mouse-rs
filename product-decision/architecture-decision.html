How to build the UI for a product you'll sell.

You loved the mockup and want it built for Windows + Linux, then tested — while keeping the door open to a paid tier and an eventual sale. That makes the GUI toolkit a load-bearing, hard-to-reverse choice. Four parallel investigations (Tauri, native-Rust toolkits, resource/reliability, and commercialization) all point the same way.

The recommendation
Build native in iced (MIT) — not a webview — as a daemon + on-demand panel.

iced is the only pure-Rust toolkit that is simultaneously permissively licensed (safe to sell closed-source), production-proven (System76 ships an entire desktop on it), resource-light, cross-compilable Kali→Windows in one command, and capable of the modern look you liked — with a software-render fallback so it runs on machines with no GPU, in VMs, and over remote desktop, which is exactly where a KVM tool gets used.

01

Why not Tauri / a webview

A webview (Tauri) would let the mockup HTML become the UI almost verbatim — genuinely tempting. But "webview" means the UI is rendered by whatever browser engine the OS ships, and that engine is different on every platform. For a product that must "run flawlessly everywhere," that's the core problem.

🪟 Windows
WebView2 (Chromium)
  • Modern engine — good
  • But runtime may be absent; guaranteeing it adds ~150 MB
🍎 macOS
WKWebView
  • Modern, ships with OS
  • Its own rendering/JS quirks vs the others
🐧 Linux — the problem
WebKitGTK (old, fragmented)
  • Fonts render too bold; glitches after updates
  • Hard libsoup2 vs 3 distro split
  • NVIDIA/DMABUF input-latency bugs
Your dev + daemon box is Kali (Linux) — the exact platform where a webview is weakest. Add two more strikes for a product: you cannot cross-compile a Tauri Windows build from Kali (it needs Windows CI runners, ~67% pricier), and you inherit a 3-engine security-patch + support surface. Tauri's headline "5 MB binary" also omits the ~100 MB system webview it borrows at runtime.

04

"Runs flawlessly on every device" — the real answer

There is no "flawless everywhere" — the failure modes just differ. The single biggest lever isn't the framework name, it's the rendering backend. Ranked most→least universally reliable, and a KVM tool lives on exactly the low-end / VM / remote machines at the top:

1
Software rendering (CPU) — Slint SW, tiny-skia
Needs no GPU at all. Runs on headless boxes, ancient laptops, VMs, over RDP, on ARM. The literal closest to "runs on anything."
most reliable
2
OpenGL / glow — egui, iced
OpenGL 2.1+ is nearly ubiquitous and usually works in VMs / remote sessions. iced falls back to software when even GL is absent — best of both.
iced lives here + rung 1 fallback
3
wgpu (Vulkan / Metal / DX12) — modern, fast
Fails on old GPUs, many VMs, and remote-desktop sessions that don't forward a GPU — unless a software Vulkan driver happens to be installed.
least universal GPU path
4
Webview — Tauri
Three different engines, a Linux libsoup version split, and a Windows runtime that may be missing. Most moving parts, least uniform.
least "just works"
05

The architecture that actually wins

The sharpest insight from the research: your performance-critical path (input capture/injection + LAN networking) is native Rust no matter what you pick for the GUI. The panel is idle 99% of the time. So split it — and the GUI's footprint stops mattering for the always-on part. Your codebase already has most of this (a headless run_blocking path + a GUI path).

always on · single-digit MB
Headless daemon
Pure Rust. Input hooks, TLS link, engine. No window, no renderer linked. This is the 99%-of-the-time process — essentially free.
performance-critical · native
on demand · dies when closed
Config panel
iced window, spawned only when the user opens settings. Talks to the daemon over local IPC. Its 30–60 MB is reclaimed on close.
the mockup lives here
thin · one event loop
Tray helper
Owns the tray icon (needs a GTK loop on Linux). Keeps the daemon a pure headless binary. Opens the panel on click.
tray-icon crate
This is smaller and more reliable than any single-process option, and it makes the open-core split natural later: the daemon/engine crates stay open (MIT), a closed pro crate compiles only into paid builds.
06

What actually bites when you sell it

Ranked by how much they'll hurt. Most are GUI-independent — but note where native's one-command Windows build and no-webview surface quietly save you money and support load.

1
Windows SmartScreen reputation
Unsigned/new-publisher installers show scary warnings until reputation builds over weeks. Fix: Azure Trusted Signing — $10/mo (no USB token, CI-friendly, now open to individuals). EV certs lost their instant-trust perk in 2024, so don't overpay.
2
Open-core split + a CLA from commit #1
To ever sell the whole product you must own every line — require a CLA before the first outside PR, keep the core MIT/Apache, and put paid logic in a closed pro crate (not behind an if licensed in open code, which is patched out in minutes). Retrofitting this later is often impossible.
3
Installers + auto-update
Native closes Tauri's one real advantage with cargo-packager (MSI/NSIS/DMG/AppImage/.deb) + Velopack (delta updates, signed, works with plain Rust). Sign update artifacts separately from the OS cert — an auto-updater is a code-execution path.
4
Paid-tier licensing + tax
Use a Merchant-of-Record (Lemon Squeezy / Paddle, ~5% + $0.50) so they remit global VAT for you. Gate features with Keygen offline signed licenses — important for a LAN tool that may be offline. macOS: $99/yr Apple Developer + notarization.
5
Support surface — native quietly wins
No webview = uniform rendering everywhere + no stale-WebKitGTK bug reports. Add Sentry + minidumps for native crashes (input hooks live near the OS and will segfault on some configs). Budget for AV false-positives — input-hooking tools get flagged as keyloggers.
07

The competition — and your wedge

Read this before building. You're entering a category with a well-funded incumbent that owns both the paid product and the open-source upstream.

📉 What killed the open-source ones
  • Synergy → went paid → community forked Barrier → InputLeap → both stalled on governance/maintainer disputes, not lack of demand.
  • Symless now owns both sides: Deskflow (OSS upstream) + Synergy 3 (paid), priced $15–29 one-time.
  • Gating encryption behind a paywall caused lasting resentment + forks.
🎯 Where you win
  • Reliability — your Rust rewrite already fixes the hang/stale-connection/freeze bugs. That's the wedge Synergy is weakest on.
  • Zero-config LAN discovery, rock-solid reconnect, clean cross-platform clipboard.
  • Never gate security (encryption) — keep TLS free. Don't move core value across the free/paid line later.
  • Clean-room Rust build (you own it) — don't fork Deskflow (GPL-2.0 would infect your paid tier).
Trademark: "Synergy" is registered. Don't pick a confusingly similar name or imply affiliation. Nominative "a Synergy alternative" marketing is fine; using their logo/name as your own is not.

One honesty note on the look: a native toolkit reimplements each visual primitive, so the mockup's glassy blur / layered soft-shadows are custom-paint work in iced. I'd adapt the design to a native-polished rendition — same themes, gradients, animated toggles, and the two-machine hero, with tasteful solid+gradient surfaces instead of literal glassmorphism. It'll read as the same product, ~85–90% of the exact mockup. If you insist on pixel-perfect HTML fidelity and accept build-on-Windows + WebView2, Tauri remains the only 100% path — but for everything else, iced is the better product decision.
