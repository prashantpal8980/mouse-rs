## The lesson from this session — read before claiming anything is done

I reported the feature complete. The owner asked "does that contain everything?" and an
audit found **four things missing**, one of them worse than missing:

**`Pacer::should_pause` was dead code.** It existed, it had a passing test, and nothing
ever called it — nor did anything ever set the `crossed` flag it reads. It looked
correct from every angle except the running program, and a green test was vouching for
it.

This is the R16 dead-knob failure again, in a worse form. The existing rule was "don't
add a setting the code doesn't honour". The rule this session adds:

> **A tested function that nothing calls is not a feature.** Before reporting anything
> complete, grep for a caller of each new public entry point outside its own tests.

The other three (speed limit, quick-send, persist history) were plainly absent. Both
kinds were only caught because the owner asked a direct question. **Treat "it's
complete" as a claim to verify, not a fact to report.**

## Known gaps — say these before the owner finds them

- **Empty directories** inside a copied folder are not recreated.
- **Symlinks** inside a copied folder are skipped, not followed (deliberate: one
  pointing outside pulls in unrelated files, one pointing inside recurses).
- **No cancel button** for a transfer in progress. The plan promised one.
- **No "always allow this size"** button on the consent banner — only "Bring it over".
- **No tray notification** for the consent prompt; the panel banner only.
- **Progress is a percentage, not a bar.**
- **X11 file publishing dies with the process** — ordinary X11 selection behaviour, but
  a not-yet-pasted file reference goes dead when mouse-rs exits.

## Hard-won rules — do not relearn these

- **A tested function nothing calls is not a feature.** New this session; see above.
- **Never add a setting the code does not read.** A dead knob looks like it works (R16).
- **Never inject synthetic input while control is on the peer** — it gets forwarded. Kali
  is the *client*, so local synthetic input is not captured; that is why the panel
  screenshots on 4 Aug were safe. On the server it would not be.
- **Never click the panel with raw screen coordinates.** `xdotool mousemove --window`
  plus a focus check.
- **Kill test instances by PID.** `pkill -x mouse-rs` would take the owner's live session
  with it.
- **A counter that cannot distinguish "it didn't happen" from "nobody tried" is not
  evidence.**
- **The consent prompt must never steal the foreground.** Windows withholds
  `WH_KEYBOARD_LL` while our own process owns the foreground window; a focus-stealing
  pop-up on every large copy would resurrect the keyboard leak.
- `export RUSTFLAGS="-L /home/kalip/mouse-rs/.xdo-shim"` for every Linux build.
- `cargo build -p mouse --no-default-features` overwrites the GUI binary at the same
  path. Rebuild with default features afterwards.
