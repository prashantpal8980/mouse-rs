## The headline: the keyboard leak is FIXED

Confirmed on hardware by the owner. Full write-up in **`docs/KEYBOARD-LEAK.md`** — read
that before touching `crates/mouse-input/src/windows.rs`.

**Root cause:** Windows does not deliver `WH_KEYBOARD_LL` callbacks to a process while that
same process owns the **foreground window**. With the mouse-rs panel focused, the keyboard
hook was never called, so keystrokes went into the panel itself. Mouse motion comes from Raw
Input on a different thread and was unaffected — that asymmetry is the signature.

**Fix:** on crossing, if one of our windows holds the foreground, hand foreground to the
user's previous window; hand it back on return.

Four earlier attempts failed because the hook was never broken — `SetWindowsHookEx`
succeeded, the pump was healthy, no stall was ever reported. It simply was not being called.
Thread priority, off-thread logging and re-arming (24/24 crossings, no effect) all fixed
plausible causes rather than the proven one.

## Reopened later the same day — two owner reports

Both were investigated; one is fixed, one is waiting on evidence from Windows.

**"The blue light doesn't show which device I'm on."** Real bug, now **fixed**. The hero
highlight used `engaged` without folding in the role, and `engaged` points at opposite
machines on the two ends of a session. On a **client** the two expressions collapse to
constants — local always lit, peer never — and Kali is the client. Present since the first
iced panel, not caused by the redesign; the redesign is when it became *visible*, because R7
shrank the hero and dropped the role labels, leaving the highlight as the only remaining
answer. `control_is_local()` in `gui.rs`, one test per role. See R15 in `UI-REQUIREMENTS.md`.

**"The keyboard leak is back on Windows."** Not reproduced from Kali and **not explainable
by the UI change** — `gui.rs` cannot disable a fix that lives in the pump loop in
`mouse-input/src/windows.rs`, and that code is intact in every build since 04:25. Two live
candidates, and they need opposite work:

1. **Windows is running a build from before the fix.** `~/mouse-serve/serve.log` records no
   fetch from `192.168.137.1` since the first fixed exe was published, and this document
   already said "Windows needs the current build installed".
2. **The fix is being refused on that machine.** `SetForegroundWindow` can accept the request
   and not move the foreground, and the original code logged that as success.

Both are now one command apart: **Step 0 of `update.md`** reports the installed hash and the
hand-off lines *before* overwriting the exe, and the pump verifies its own hand-off 120 ms
later and logs `the foreground did NOT leave this process` when it was refused. See the new
section in `docs/KEYBOARD-LEAK.md`.

Note the panel is what creates the condition the fix neutralises, so the two are not
independent in practice: a panel the owner spends more time inside (five tabs, a ⋯ menu, a
Detect button) holds the foreground more often, and every one of those crossings depends on
the hand-off working.

## Hard-won rules — do not relearn these

- **Never inject synthetic mouse input while control is on the peer.** It gets forwarded to
  the other machine. A Windows session tried to click the tray and sent real clicks onto the
  owner's Kali desktop. The update prompt now forbids synthetic input outright and stops
  mouse-rs with `Stop-Process` instead of clicking.
- **Never click the panel with raw screen coordinates.** Use `xdotool mousemove --window`
  plus a focus check. Blind absolute clicks changed the owner's `entry_edge` mid-test —
  twice this session automated clicking altered live settings.
- **A counter that cannot distinguish "it didn't happen" from "nobody tried" is not
  evidence.** `hook_calls=0` was ambiguous until Raw Input witnessed whether the user had
  typed at all — and that ambiguity had already produced one confidently-wrong leak rate.
- **Don't trust a clean run from an instrument that cannot see the failure.** An earlier
  build "passed" 18 crossings; it had no `hook_calls`, so a dead hook logged as healthy.
- **A placement change must move controls, not re-author them.** Rebuilding tabs from
  scratch silently dropped the lock hotkey, return hotkey, Show/Hide secret and the
  edge-overlap warning.
- **Write requirements down when agreed, not when built.** "Restore defaults" was lost
  entirely because it lived only in conversation. `docs/UI-REQUIREMENTS.md` exists for this.
- `export RUSTFLAGS="-L /home/kalip/mouse-rs/.xdo-shim"` for every Linux build, or linking
  fails with `-lxdo`.
- `pkill -f <pattern>` matches the shell running it. Use `pkill -x mouse-rs`.
