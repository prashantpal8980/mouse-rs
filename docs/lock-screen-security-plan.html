The lock-screen unlock password

A second password, owned by mouse-rs, that has to be given before the other computer's keyboard can type anything into a login or lock screen. This page explains the idea, how the encryption works behind it, and the decisions we still need to make.

Design proposal · 15 Oct 2026 · not built yet. The owner's plan is to build it after the Linux↔Windows, Linux↔Linux and Windows↔Windows role tests are done.

1. The idea in one picture

Today, once the laptop is paired, its keyboard can type into Kali's login screen straight away. Anyone sitting at the laptop can therefore start guessing Kali's login password. The new rule:

Nothing typed on the other computer reaches a login or lock screen until the mouse-rs unlock password has been given correctly. The computer being protected (Kali in our setup) checks that password itself. It never takes the other computer's word for it.

So there are two passwords, and they do different jobs:

NEWmouse-rs unlock password
Belongs to mouse-rs. Proves that the person at the other computer is allowed to type into this machine's login screen at all. Set once in Settings → Security & pairing, on the machine it protects.
UNCHANGEDKali's own login password
Belongs to the operating system. mouse-rs never sees, stores or checks it. It only delivers the key presses, and only after the unlock password was right.

2. Who we are protecting against

AttackerWhat they could do todayAfter this plan
A stranger on the same Wi-Fi or router Can't connect without the shared secret. GAP They can pretend to be the server; see section 3. Blocked. Each machine checks the other's pinned key.
Someone sitting at the unlocked laptop (left unattended, borrowed, stolen) Can move to Kali's login screen and guess Kali's password as often as they like. Must know the unlock password first. Kali allows only a few tries, then waits longer and longer.
Someone who copies the laptop's settings file (backup, malware, a stolen disk) The shared secret sits in that file and works on its own: they can connect as the laptop. The file holds no password and nothing password-like. Copying it does not give them the unlock password.
Someone who copies Kali's stored record Same as above: the secret is stored in the clear in /etc/mouse-rs. The record cannot be used to unlock ("pass the hash" does not work). The best they can do is guess passwords offline, and each guess costs a deliberate ~0.5 s and 64 MB.
Someone recording the network traffic Sees only encrypted data. Same, and nothing in the recording helps them guess the password, even if they later steal a key.
What no software design here can stop: someone who knows both passwords; a keylogger or other malware already running on the laptop; someone watching over your shoulder; a person with physical root access to Kali itself. This plan narrows the attack to "must know a secret that only you know". It does not make a compromised computer safe.

3. What mouse-rs does today, and a gap found while writing this

Today's link has two parts (crates/mouse-core/src/tls.rs and auth.rs):

  1. TLS encryption. The server makes a new certificate each time it starts. The client encrypts with it but does not check whose certificate it is; the code says so: "encrypts but does not verify the cert's identity".
  2. Shared-secret check (HMAC-SHA256). The server sends a random challenge; the client answers with HMAC(secret, challenge); the server checks it.
The gap: only the client proves who it is. The server never proves anything.
The server simply replies "ok", and the client believes it. So a machine on the network that gets Kali to connect to it can play the server, by taking over the 192.168.137.1 address or answering in its place. Kali would then accept its mouse and keyboard, including at the login screen. Beacons are sealed with the secret, so the attack can't come through discovery, but it can through the fixed server address.

A fake server would also receive HMAC(secret, challenge) for a challenge it chose. That is enough to test guesses of the secret offline. A 32-character generated secret is far too strong to guess, but a short secret typed by hand is not.

Recorded as B34 in KNOWN-ISSUES. Layer 1 below closes it. It is worth fixing before launch, whenever the unlock password itself is built.

4. "Hybrid" encryption, explained simply

You remembered a "hybrid" approach. That is the right word. There are two families of encryption, and every modern secure link uses both together:

Asymmetric (public / private key)
Each side has a key pair. The public half can be shown to anyone; the private half never leaves the machine. Two strangers can use it to agree on a secret over an open wire, and to prove identity by signing. It is slow, so it is only used for the first moments of a connection.

Used here: X25519 (agreeing a key) and Ed25519 (identity signatures).
Symmetric (one shared key)
Both sides use the same key to lock and unlock. It is extremely fast; it carries every mouse move, key press and gigabyte of pasted file. The hard part is getting the same key to both sides safely, and the asymmetric half solves that.

Used here: AES-256-GCM or ChaCha20-Poly1305.
Hybrid = asymmetric to agree a fresh key, then symmetric for all the data. TLS 1.3, which mouse-rs already uses, works exactly this way. Each connection gets brand-new keys and throws them away afterwards ("forward secrecy"), so a key stolen next year can't decrypt traffic recorded today.

There is a newer meaning of "hybrid" too: post-quantum hybrid. It mixes classic X25519 with ML-KEM-768, a key agreement designed to resist future quantum computers, so the link stays safe unless both are broken. rustls offers this as X25519MLKEM768 through its aws-lc-rs backend. mouse-rs uses the ring backend today because it cross-compiles cleanly to Windows, so switching needs a build check first. This is a nice extra, not essential for a LAN tool.

The other half of your question: the password is not encrypted. A password should never be stored in a form that can be turned back into it. It is turned into a one-way slow hash, and for the unlock password we go one step further with OPAQUE (section 5, Layer 2). There, even the hash is useless to a thief for logging in.

5. The proposed design: three layers

LAYER 1
The machines know each other
Device keys, paired once, checked by both sides on every connection. Closes the B34 gap.
LAYER 2
The unlock password
OPAQUE plus Argon2id. Proves you know the password without sending it, and a stolen record can't be used to unlock.
LAYER 3
Brute-force limits
A few tries, then growing delays, a lockout that survives restarts, and alerts.

Layer 1: device keys and pairing

  • Each install creates an Ed25519 key pair once. The private key stays on that machine: in a root-only file on Linux, and protected by Windows DPAPI on Windows.
  • Pairing happens once. One machine shows a 6-digit code and you type it on the other. A PAKE (SPAKE2 or CPace) turns that short code into a strong, verified exchange of public keys. Someone eavesdropping or impersonating gets a single guess at the code, and a wrong guess ends the pairing.
  • From then on, the TLS link is mutual: each side checks that the other presents the exact public key it paired with ("pinning"). An impostor fails at once, and the shared secret in the settings file goes away.
  • Settings → Security & pairing lists paired machines with a short fingerprint each, and a Forget button for each one.

Layer 2: the unlock password (OPAQUE)

OPAQUE is an IETF-standard "augmented PAKE". In plain words:

  • Setting it (on Kali, as administrator, in Settings → Security & pairing). Kali stores a registration record. That record is not the password and not a hash that can be replayed.
  • Using it. The laptop and Kali run a short exchange. Kali learns only "this person knows the password", and the laptop learns only "this really is Kali". The password, and any hash of it, never crosses the wire. Not even a fake Kali would receive anything it could test guesses against.
  • Why "they can't use the hash". With an ordinary stored hash, a thief can sometimes present the hash itself in place of the password ("pass the hash"). OPAQUE's record does not work that way: presenting it achieves nothing. To get anywhere, the thief must recover the actual password by guessing.
  • Making guessing expensive. Inside OPAQUE, the password is stretched with Argon2id, set to about 0.5 s and 64 MB per guess. A thief with the record can then test only a few guesses per second per CPU core, instead of billions. A decent passphrase stays out of reach.
  • The check runs on the machine being protected (Kali's root service). A modified laptop app can't skip it, because Kali throws away every key event until its own check has passed.

Layer 3: brute-force limits (enforced by Kali)

Failed tries in a rowWhat Kali does
1–3Says "wrong password" and lets them try again.
430-second wait.
52-minute wait.
610-minute wait.
7 or moreLocked until someone logs in at Kali's own keyboard (or a 24-hour wait; your call).
  • The counter is kept on disk on Kali, so restarting either app does not reset it.
  • A successful unlock is valid only for that one login screen. It ends when the session opens, after 2 minutes of no input, or when the link drops. The next lock screen asks again.
  • After you log in, Kali shows "3 failed unlock attempts from MSI at 02:14", and the attempts go into the shipped log, never with the typed text.
  • Kali refuses the attempt if the laptop isn't a paired device (Layer 1), so a stranger never even reaches the password prompt.

6. Your scenario, step by step

The laptop is the server; Kali was just switched on and is showing its login screen.

  • Kali bootsThe root login-screen service starts and links to the laptop. Both sides check each other's pinned key (Layer 1).
  • You move the mouse to KaliKali says "login screen, locked". The pointer may move (your call, question 2 below), but key presses are dropped.
  • The laptop shows the unlock promptYou type the mouse-rs unlock password into the laptop's own dialog. Those keys stay on the laptop.
  • Wrong passwordKali counts it and applies the delays above; nothing reaches the login screen.
  • Right passwordThe OPAQUE check passes on Kali, and Kali opens the gate for this login screen only.
  • You type Kali's own login passwordKali's login screen checks it as usual. mouse-rs only delivered the keys.
  • The session opensThe gate closes again. The normal desktop instance takes over, as it does now.

8. Decisions to talk through

1. Where is the unlock password typed?
In a dialog on the laptop (shown above), or on Kali's screen inside a small mouse-rs box on the login screen?
Suggested: on the laptop. Drawing our own box on top of a login screen is fragile and differs for every desktop. A laptop dialog is simple, and Kali still does the checking.
2. Before unlocking, may the mouse move on Kali, or nothing at all?
Suggested: the pointer may move, but no clicks or keys. Then you can see the link works. A click on "Restart" or "Shut down" on a login screen is a risk, so clicks stay blocked.
3. Only the boot login screen, or the screen lock too?
When Kali locks itself after idle, the normal desktop instance is the one typing into the lock screen, not the root service. Should that also ask for the unlock password?
Suggested: yes, both. Otherwise anyone at the laptop just waits for the screen lock instead of a reboot.
4. What happens after 7 wrong tries?
Locked until someone logs in at Kali's own keyboard, or locked for 24 hours?
Suggested: until a local login. That is the safest choice, and you can always log in at Kali directly.
5. Forgotten unlock password?
Suggested: reset it on Kali itself, as administrator, in Settings → Security & pairing. There is no recovery over the network, by design.
6. One unlock password per machine, or one for all your machines?
Suggested: per machine. Each machine sets its own and stores its own record, so a leak on one machine does not unlock the others.
7. Is it on by default?
Suggested: login-screen typing stays off until an unlock password is set. Then the feature can never be on without a password.
8. Windows as the protected machine.
Typing into the Windows login screen isn't possible today (B9: Windows walls off its login desktop). When it is built, it gets the same gate. macOS will work the same way.

9. Order of work (when we start)

  1. Finish the role tests: Linux→Windows, Linux→Linux, Windows→Windows (B33). This comes first, as you decided.
  2. Layer 1: device keys, pairing code and mutual pinned TLS. This replaces the shared secret and closes B34.
  3. Layer 2 and Layer 3: the unlock password with OPAQUE and Argon2id, the brute-force limits, and the prompt on the laptop.
  4. Attack tests, run here on Kali: a fake server, a stolen settings file, a replayed record, repeated wrong passwords, and restarting to reset the counter. Each must fail.
  5. Your hardware test at a real login screen.
