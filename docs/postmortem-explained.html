Why Ctrl stopped working

A fix for an occasional stuck Alt made every modifier chord unusable for six hours.

mouse-rs · 9 October 2026 · post-mortem

Impact
Ctrl never reached Kali at all → Ctrl+Space dead. Alt+Tab worked ~1 press in 5.
Duration
~6 hours, on the Windows laptop only
Trigger
A fix I shipped for B13 (the intermittent stuck Alt+Tab)
Resolved by
Withdrawing the fix, then rolling the laptop back to the 4 Sep build
Data loss
None

01What happened

  • 18:18 B13 diagnosed from the shipped logs. Cause recorded as a Windows hook blackout mid-chord. This diagnosis was wrong.
  • 18:43 Receiving-side mitigation — release a modifier held through 5 s of total silence. Sound, and still in place today.
  • 19:05 The “cure” shipped to the laptop. Compared what we’d told Kali was held against what Windows said was physically down.
  • ~19:30 Owner installs it. Keyboard chords stop working.
  • 20:11 Reported: “unable to use ctrl + space”, then “not sharing ctrl now… alt+tab only work when i click like 5 time”.
  • 20:33 Cause found and fix withdrawn. Guards added that run on the build host.
  • 21:56 Owner asks to roll back rather than forward. The 4 Sep build is rebuilt and served.
  • 22:2x Three failed install attempts — each for a different avoidable reason.
  • 22:4x Working again.

02The mechanism

The fix asked Windows “is this key really held?” — a question Windows cannot answer about a key we swallowed ourselves.

While control is on Kali, mouse-rs must stop keystrokes from also landing on Windows. It does that in a low-level keyboard hook by returning 1, which tells Windows to discard the event. The crucial detail is where that hook sits: everything that could later report key state is downstream of it.

So for every modifier the owner held, Windows reported it as up. My code read that as “the release got lost” and helpfully sent a release — about 8 ms after the press.

Alt+Tab “works on the fifth try” is the same bug. Tab only counted if it landed inside the few milliseconds before the sweep killed Alt. Pressing repeatedly eventually won that race.

03The proof was already in the log

A counter added months ago, for an unrelated question, settles it completely.

768
hook_calls
414
swallowed
0
raw_keys

Raw Input is a separate delivery path from the hook chain, which mouse-rs already registers as an independent witness. It saw none of the 414 suppressed keys. That is the measurement that proves no Windows API can observe a key we swallow — and therefore that no fix of that shape can ever work.

It was one grep away, in the same source file, before I wrote a line of the fix.

It also refutes my diagnosis of the original bug. I had claimed a higher-integrity window kills our hook mid-chord. But hook_calls was never once zero, and the purpose-built “the hook was dead” diagnostic has never fired. B13’s real cause is still unknown — the bug list now says so instead of asserting a mechanism.

04Five failures, not one

The bug was the small part. Each of these is independently worth fixing.

01A premise I never measured

I believed GetAsyncKeyState sees through hooks, wrote that in a doc comment, and treated having written it down as having established it.

The disproof was a counter in the same file.

02Evidence about the wrong moment

I cited 24 CROSSING WILL NOT WORK warnings as proof of a mid-chord hook blackout. Those fire at crossing start, about whether a crossing can begin at all.

I never went looking for evidence that would disconfirm the theory — though it was being logged all along.

03Tests that couldn’t catch it, twice over

They never ran. They live in windows.rs, which only compiles for the Windows target — on the Linux build host they compile and never execute. “213 tests pass” was true and meaningless.

They tested the wrong thing. They pinned a pure function that encoded the false premise. A test of a false premise passes. Nothing asserted the behaviour that mattered: press Ctrl, press Space, Ctrl must still be held.

04A constant fix for an occasional fault

B13 was intermittent and self-recovering. The fix ran every 120 ms, on every modifier, always. Its failure mode was total.

I never asked what happens if it’s wrong. The answer was “the keyboard stops working” — far worse than the symptom being treated.

05A recovery that failed three more times

Overwrote the only working exe before verifying the download. Printed installed after Move-Item had errored. Assumed a normal shell could stop an elevated process. Handed over multi-line blocks that PowerShell silently chops at blank lines.

Then the obvious one-liner was broken too: the server sends .ps1 as binary, so iex (iwr).Content gets a byte array. Found by running it, not reading it.

05The common cause

Reasoning substituted for measurement, in an environment where the code cannot be executed.

Windows code can’t run on the Kali build box. The laptop is the only place it runs, and it’s tested by hand. That makes confident-sounding prose the cheapest thing to produce and the least reliable thing to ship. Four of the five failures would have been caught by running or grepping something already present — pwsh is even installed locally, which is how the iex bug got caught before it was sent.

06What changed

RuleConcretely
State the premise, name the measurementFor any platform-API fix, write the premise and the evidence confirming it, before the code. No evidence → ship a diagnostic first.
Host-executable, or not testedInput-path fixes need a test that runs on the Linux host and asserts user-visible behaviour. Windows-target tests are documentation.
Prove a guard bitesConfirm a new test fails against the faulty behaviour before keeping it. Done for the chord test.
Match blast radius to the faultNothing runs continuously to correct an occasional, self-recovering fault.
Don’t say “fixed” firstLogs upload automatically. Read them after one crossing before using the word.
Never overwrite the last good artifactVerify the replacement first; keep a .bak; check post-conditions instead of assuming the previous line worked.

07What worked, and is worth keeping

Log shipping made this conclusive in minutes. Both machines upload to ~/mouse-reports. The smoking-gun trace came from the receiver’s own log with millisecond timestamps — nothing had to be reproduced or pasted.

A cheap counter paid for itself. raw_keys was added to tell “the hook was dead” apart from “nothing was typed”. It’s what proved no API can see a suppressed key.

The standing bug list preserved the history, so a wrong diagnosis could be corrected in place rather than quietly forgotten.

The report named both symptoms. “Ctrl isn’t sharing” and “Alt+Tab takes 5 tries” were two faces of one cause — having both made the shared mechanism obvious immediately.
