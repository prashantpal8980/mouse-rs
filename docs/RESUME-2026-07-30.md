## The one thing that matters most

**The keyboard still leaks in real use, ~1 in 10–20 crossings, and the root cause is NOT
yet established.** Everything else here is secondary.

The user found a **reproducible trigger**, which is the most valuable fact we have:

> If the mouse-rs panel itself is the focused window when you cross to Kali, the keyboard
> is not shared — the mouse crosses, the typing stays on Windows.

### Leading hypothesis — pump starvation

Low-level hook callbacks are delivered **on the capture pump thread**, during its message
pump. If one iteration exceeds Windows' `LowLevelHooksTimeout` (~300 ms default), the OS
stops waiting and **skips the hook entirely** — the keystroke goes straight to the local
app and our code never sees it. No leak counter can ever catch that case, which is why the
old `DIAG_*` counters reported `swallowed=231, leaked=0` while the user was still seeing
leaks.

Why the focus clue fits: a focused panel renders continuously through wgpu, so the process
is at its busiest exactly when the user says the bug appears.

**Second candidate:** `suppress` and the hook's `grabbed` flag reconcile every ~8 ms; a key
pressed inside that window sees "not suppressing" and passes through.

### Already ruled out

The in-hook failsafe key. `"ctrl+win+alt+esc"` is not a single named key, so `parse_hotkey`
returns `None` and `windows.rs:1039` falls back to **Scroll Lock**. A stray Escape cannot
silently drop suppression.

### The instrument is built and shipped (commit `adb4246`)

Three mutually-exclusive diagnoses, all silent unless something is wrong:

```
INFO  keyboard grabbed (control moved to the peer)
      focus='mouse-rs' class=Window Class pid=8412 (THIS IS OUR OWN PANEL)
WARN  KEYBOARD LEAK: keystroke stayed on this machine
      vk=0x41 reason=suppress_requested_but_not_grabbed leak_n=1
WARN  capture pump stalled while suppressing — Windows may have SKIPPED the
      keyboard hook  stalled_ms=312
WARN  keyboard released — SOME KEYS LEAKED  swallowed=118 leaked=3 remote_ms=64500
```

How to read the result:

| What appears | Diagnosis |
|---|---|
| `pump stalled` warning | Windows skipped the hook. Fix = get work off that thread / raise timeout. |
| `KEYBOARD LEAK … not_grabbed` | The grab race (~8 ms window). Fix = grab before the crossing commits. |
| Neither, but the bug still happened | Keys left Windows fine — the problem is on Kali's side (inject/network). |

All of this is **Windows-only code** (`crates/mouse-input/src/windows.rs`), so the Kali
binary needs no rebuild for it.

## Two open items the retest raised, not yet acted on

1. **`Quit` is silent in the log.** Fix 4 covered the Stop button but not the shutdown path,
   so a Quit — even one tearing down a live session — writes nothing. A deliberate exit and
   a crash are still indistinguishable. One line in the shutdown path closes it.
2. **The panel has no accessibility tree at all** (zero UI Automation descendants). Screen
   readers can't see it and automated UI testing can't drive it — the Windows tester had to
   use synthetic clicks, ~3 of which drop per run. An iced/wgpu property, not our code, but
   worth a deliberate decision before shipping a paid product.

## Build gotchas that have each cost real time

- **Always** `export RUSTFLAGS="-L /home/kalip/mouse-rs/.xdo-shim"` for Linux builds. Only
  runtime `libxdo3` is installed, so linking fails with `unable to find library -lxdo`.
  `cargo check`/`clippy` pass without it — only linking fails, which reads like a packaging
  problem rather than a missing flag.
- `cargo build -p mouse --release --no-default-features` writes to the **same path** as the
  GUI build. It leaves a headless binary at `target/release/mouse-rs`, and the next bare
  launch logs "built without the `gui` feature" and exits. Rebuild with default features.
- `pkill -f <pattern>` and `pgrep -f <pattern>` **match the shell running the command**.
  This killed the working shell three times in one session. Use `pkill -x mouse-rs`
  (process name) or filter out `$$`.
- Never test the window ✕ with `xdotool windowclose` — it destroys the window instead of
  sending `WM_DELETE_WINDOW` and fakes convincing crashes. Use Alt+F4. (TESTING.md §6b)
- The process owns **two** X11 windows named `mouse-rs`: the real 600×840 panel and a 10×10
  permanently-unmapped gtk tray helper. `xdotool search | head -1` may return the helper.
