Why the RAR crawled

The congestion control acted on one measurement hundreds of times.

The transfer was not slow because of the RAR, the disk, or the link. Those were fine. It was slow because the code that decides how fast to send was reading a two-second-old latency reading and treating it as fresh news, over and over.

The mismatch

Two clocks run inside a transfer, and they run at wildly different speeds.

Latency is measuredheartbeat — every 2 s
1 sample
The rate is re-decidedonce per 256 KB chunk
~800 decisions
In one heartbeat window at full speed, one measurement is available and 800 decisions are made from it.

That is fine as long as each decision reads the measurement. The bug was that each decision acted on it — and the action was to halve the send rate.

The collapse

One slow heartbeat, and the rate is cut in half 800 times in a row before a second opinion can possibly arrive. It only takes eleven of those to hit the floor.

Halving is instant. Recovery adds 1 MB/s per chunk — and at the floor, one 256 KB chunk takes 4 seconds.

That last line is the trap. The collapse destroys the very thing recovery depends on. At full speed the pacer gets 400 chances a second to climb back; at the floor it gets one every four seconds. So it sat near the bottom until the next heartbeat, climbed a little, and was flattened again by the next stale sample. Averaged over the RAR, that sawtooth came out at 8.1 MB/s.

The fix

Number the measurements. A back-off remembers which sample caused it and refuses to fire twice on the same one — one measurement, one halving. Between samples the rate is held rather than cut again on evidence already acted upon.

Before
// once per 256 KB chunk
if health.is_congested() {
    rate = (rate / 2)
        .max(MIN_RATE);
}
// 800 chunks per sample
// = 800 halvings
After
// once per 256 KB chunk
if health.is_congested() {
  let s = health.sample_id();
  if s != self.backed_off_on {
    self.backed_off_on = s;
    rate = (rate / 2)
        .max(MIN_RATE);
  }
}

LinkHealth gained a samples: AtomicU64 counter that ticks on every round-trip measurement; Pacer gained backed_off_on to remember the last one it responded to.

A test was asserting the bug

Worth saying plainly: an existing test, the_pacer_backs_off_hard_and_recovers_gently, required the rate to collapse to the floor after 100 reads of one sample. It passed the whole time. The defect had been written down as intended behaviour, which is why nothing caught it. That test now asserts one halving per sample.

A second, smaller brake

While your pointer is on the other machine, transfers are capped so the mouse stays responsive. That ceiling was set at 2 MB/s back when the alternative was stopping transfers dead — against a full stop, anything moving looked generous.

Rate cap2 MB/s 16 MB/s

Share of a gigabit link2%13%

It is a hard cap that ignores how good the link actually is, so on a wired gigabit connection it was discarding 90% of the line during the exact minutes you are most likely to be watching. The real protection against lag is the pacer backing off when latency genuinely rises — this is only a belt-and-braces ceiling, and 16 MB/s is still a small share of the cable.

How this was found

  1. Read the shipped logs, not the symptom Both machines upload their own logs. 4.28 GB / 507 s came straight out of the transfer records — no guessing, and nobody had to be asked.
  2. Rule out the obvious suspect The 2 MB/s crossed-cap would explain it — but control was on Kali for only 10% of that window, so it could not account for the other 90%.
  3. Compare the two clocks Heartbeat every 2 s; Pacer::step() once per 256 KB. That ratio is the whole bug.
  4. Check the arithmetic against the observation Eleven halvings reach the floor; the floor makes a chunk take 4 s. The sawtooth that predicts averages out near 8 MB/s — which is what was measured.

Where it stands

Both machines are running the fixed build (E8A7C3FE…, 12,080,128 bytes). Kali reconnected at 11:47:02 with the bulk lane up and log shipping on. 185 tests pass, clippy clean on both targets.

The next large copy should hold near line rate instead of sawtoothing. If it does not, the logs will already be on the server — nothing needs to be captured by hand.
