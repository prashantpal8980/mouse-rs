2. Saving your config could have destroyed your shared secret

fixed

Both machines. The most dangerous of the six.

Pressing Start silently rewrote config.json — and it did it by emptying the file first, then writing the new contents:

OLD WAY:   [ truncate config.json to 0 bytes ]  →  [ write new contents ]
                              ↑
                    crash / power cut here
                    = empty config, shared_secret GONE

NEW WAY:   [ write config.json.tmp ] → [ flush to disk ] → [ atomic rename over config.json ]
                              ↑
                    crash anywhere here
                    = original file untouched

The secret is the one value in there that can't be recreated — lose it and both machines stop trusting each other until you re-pair them. Retest confirmed: 7 saves, zero leftover temp files, secret intact.

Your phrase for it — "mouse is on kali, why keyboard is on windows" — is exactly this. It's one bug, not two.

A keystroke has to survive five steps to reach Kali. A leak means one of them failed, and right now the log can't tell me which:

1
Windows calls our keyboard hook — if the hook is too slow, Windows skips it entirely and the key goes straight to the local app. Windows allows roughly 300 ms. This was a real bug once already, fixed by moving mouse handling to its own thread. Under load it could still happen — and it would look exactly like what you describe: intermittent, no pattern.
2
The hook checks "am I suppressing?" — the crossing flag and the hook's own state are reconciled every ~8 ms. A key pressed inside that window sees "not suppressing" and passes through. A prime suspect for a 1-in-15 rate.
3
The hook swallows the key so no Windows app sees it. Was proven working — 231 swallowed, 0 leaked — but that proof came from counters I have since deleted.
4
The key is sent over the network — if the link stalls, keys can be dropped in flight while the mouse still looks fine.
5
Kali injects the key — if injection fails there, the key is lost silently and it looks identical to a leak on Windows. This is why logging is needed on both machines, as you said.

Why I can't answer this today: the counters that measured steps 1–3 were in the build until I removed them a few hours ago, because an automated test said the keyboard was proven working. Your experience says otherwise, and you're the one actually using it. Removing them was the wrong call.

2D. Clipboard doesn't copy images

never built

Both machines. Not a bug — the feature was never written.

I checked the code rather than guessing. The network protocol reserves a message type for images, but the clipboard code is text-only, and an arriving image message is explicitly thrown away. The comment in the source says it outright:

// Text only for now. The protocol's `ClipboardImage` is reserved for a later pass
...
Ok(_) => {} // ClipboardImage and any stray message: ignored for now

So no amount of logging will explain this one — there's nothing to log, because nothing ever attempts it. Copying an image will do nothing until image sync is built: read the image off the clipboard, size-limit it, send it, write it to the other clipboard. That's a feature to schedule, not a fault to find.

Worth knowing: the old Python version left a clip_images folder in .mouse_share, so it may have attempted this. If image copy used to work for you under the Python build, tell me — that changes it from "new feature" to "regression", and I'd look at what Python did.

3 — The logging you asked for

You said: make a log mechanism so we can figure out each issue without struggling. Here's exactly what I'd add. Nothing below is built yet — I want you to see the shape first, because you're the one who'll be reading the output.

Every leak gets a line, on the machine where it happened

Instead of a counter you have to interpret, a leak announces itself with a reason:

WARN  kbd LEAK  vk=0x41 'A'  reason=hook_not_suppressing  since_crossing=142ms  leak#3
WARN  kbd LEAK  vk=0x42 'B'  reason=state_borrow_busy       since_crossing=1.2s   leak#4
INFO  kbd state grabbed=true suppress=true  (crossing #12 → remote)
INFO  kbd 118 keys swallowed, 0 leaked, this remote session

The reason field is the whole point — it names which of the five steps failed, so we stop guessing. since_crossing tests the timing-race theory directly: if leaks cluster in the first few milliseconds after crossing, that's step 2 and I know how to fix it.

Both sides count the same keys, so we can see where they vanish

Windows — server

sent 118 keys
swallowed 118, leaked 0
→compare
the counts

Kali — client

injected 118 keys
failed 0

Three possible readings, each pointing somewhere different:

  • Windows leaked > 0 → the hook failed. A Windows-side problem, steps 1–3.
  • Windows sent 118, Kali injected 110 → keys died on the network or on injection. Steps 4–5, and nothing to do with the hook.
  • Counts match but you still saw wrong behaviour → the keys arrived and went to the wrong application on Kali. A different bug entirely.

Right now all three look identical from the outside, which is exactly why this has been so annoying to pin down.

Kept quiet by default, loud on demand

The reason I deleted the old counters is that they wrote a line every second, forever. The replacement:

  • Leaks are always logged — they're rare and they matter. A leak should never be silent.
  • One summary per crossing, not one line per second: keys swallowed, keys leaked, longest hook delay.
  • Full per-key detail only with RUST_LOG=debug — available when hunting, absent otherwise.

That gives you a log that stays small and readable but still catches a 1-in-20 event, because the rare thing is the thing that always gets written.
