1 · How it works

There are two copies of mouse-rs on Kali, and only one of them runs at a time. At the login screen nobody is logged in, so the normal app can't run yet. A separate background service takes its place until you log in.

Windows laptop

mouse-rs (the server)

Owns the real keyboard and mouse. When the pointer leaves the screen edge, it sends every movement and key to Kali.

⟶encrypted link
port 24800
Kali · before you log in

Login-screen service

A system service that starts at boot, before any user. It runs as root and types into the login screen through a virtual keyboard (uinput).

Kali · after you log in

Your normal mouse-rs app

Starts with your desktop. It adds the clipboard, files and the control panel.

1. BootThe service starts and connects to the laptop. Kali's login screen can now be controlled from the laptop.
2. You type the passwordMove the laptop pointer onto Kali, then type. The keys travel over the link and the service types them into the login screen.
3. HandoverOnce you're logged in, the service sees your session and steps aside. Your normal app connects about 10 seconds later.

3 · Why it didn't work last time

The software behaved the same both times. The difference was whether the pointer reached Kali before the password was typed.

12 October: you typed on Kali's keyboard

  • The service connected at 08:33:17, two seconds after it started.
  • The laptop's pointer never crossed onto Kali. The laptop log has no "crossed to remote" line.
  • The password was typed on Kali's own keyboard at 08:33:26.
  • Nothing told you Kali's login screen was ready, or that you had to move the pointer across first.

13 October: you typed on the laptop

  • The service connected the same way, in under a second.
  • You moved the pointer across, and on the fifth try it stayed on Kali.
  • You typed on the laptop, and the keys reached the login screen.
  • No code changed on Kali in between: it still runs the 9 October copy.

Problems the logs showed, all fixed in the newer build that isn't installed yet:

  • You had no cue. The new laptop build shows a toast and labels the peer "kali-desktop (login screen)" when Kali is waiting at its login screen.
  • Key names went into the log. The old copy logged the first 8 keys of each crossing by name. This morning those were arrow keys, so no password letters were recorded, but a password could have been. The new copy never logs key names at the login screen.
  • The laptop sent your clipboard to the login screen. 216 bytes of copied text went to it this morning. The new laptop build doesn't send the clipboard there.
  • It restarted every 3 seconds. While you're logged in, the old copy has restarted 172 times today. The new copy waits quietly instead.
  • Its log never reached you. The old copy's log stays inside Kali. The new copy ships it to ~/mouse-reports/kali-desktop-login-screen-mouse-rs.log, so I can read it after a reboot.

4 · The command I asked you to run, explained

The login-screen service runs its own protected copy of mouse-rs, and that copy is still from 9 October. This command replaces it with today's build. It needs administrator rights (sudo), which I'm not allowed to use, so you have to run it. Click each part to see what it means.

Type this into the Claude Code prompt, exactly as shown:

! sudo /home/kalip/mouse-rs/target/release/mouse-rs greeter-install

What it changes on Kali

StepFileWhy
Copies your settings/etc/mouse-rs/config.jsonThe laptop's address and the shared secret. The service can't read your home folder, and only root can read this copy.
Copies the program/usr/local/bin/mouse-rsReplaces the 9 October copy with today's build, which has all the fixes listed above.
Writes the service definition/etc/systemd/system/mouse-rs-greeter.serviceTells Linux to start it at every boot.
Loads the virtual keyboard driver/etc/modules-load.d/mouse-rs-uinput.confMakes sure uinput is loaded at boot.
Enables the servicesystemctl enableTurns it on for the next boot.
It won't interrupt sharingYour running mouse-rs app isn't touched. The new copy only takes over at the next login screen.
It asks for your passwordThat's sudo confirming it's you. The password isn't stored or logged.
Success looks like thisIt prints "Installed." and three lines naming the config, service and binary.
You can run it againRun it again whenever I say there's a newer build. greeter-uninstall removes the service completely.

To check it worked, run /home/kalip/mouse-rs/target/release/mouse-rs greeter-status (no sudo needed). The line old binary is an older build than this one should be gone, and every line should read ok. I also changed the install so it can't fail with "Text file busy" while the old copy is restarting.
